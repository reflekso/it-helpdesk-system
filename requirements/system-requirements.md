# Требования к ПО

# Описание

Эта спецификация требований к ПО описывает функциональные и нефункциональные требования к выпуску 1.0 "Сервис заявок в IT-поддержку". Этот документ предназначен для команды, которая будет реализовывать и проверять корректность работы системы.

# Функциональные требования

## 1. Авторизация и управление пользователями

### FR-1. Авторизация

1. В системе должна быть возможность авторизации пользователей через логин и пароль.

### FR-2. Управление пользователями

 1. Система должна позволять Администратору создавать, просматривать, редактировать, удалять аккаунты пользователей.
 2. Аккаунты Администратора и Аудитора задаются в системе при ее развертывании.
 3. При создании аккаунта Сотрудника обязательными полями являются: логин, пароль, роль, фамилия, имя, рабочий отдел, рабочее место.
 4. При создании аккаунта Специалиста обязательными полями являются: логин, пароль, роль, фамилия, имя, рабочий отдел.
 5. Система не должна позволять создавать аккаунты с одинаковым логином.
 6. При просмотре данных система отображает Администратору следующие данные о пользователе: ID, логин, роль, фамилия, имя, рабочий отдел, рабочее место (только у Сотрудника).
 7. Система должна позволять Администратору **редактировать** следующую информацию о созданном пользователе: логин, роль, фамилия, имя, рабочий отдел, рабочее место (только у Сотрудника).
 8. Система должна позволять Администратору **сбрасывать** пароль любому пользователю и давать возможность задать ему новый пароль.

## 2. Управление заявками со стороны Сотрудника

### FR-3. Просмотр и история заявок

1. Система должна позволять Сотруднику смотреть следующую информацию о его заявках: номер, категория, дата создания, описание проблемы, фамилия и имя Специалиста, работающего с заявкой (если он уже назначен), статус.
2. Система должна отображать заявки с информацией о них, отсортированные по дате и времени (от новых к старым).

### FR-4. Создание заявок

1. Система должна позволять Сотруднику создавать заявку в отдел IT-поддержки с выбором категории и текстовым описанием проблемы.
2. Система должна блокировать отправку формы Сотруднику, если у него уже есть заявка с любым статусом, кроме "Закрыта".
3. При успешной отправке формы Система должна записывать заявку со статусом "Создана".

### FR-5. Жизненный цикл заявки

1. Система должна позволять Сотруднику подтверждать выполнение заявки Специалистом, если Сотрудник имеет активную заявку со статусом "Закрыта специалистом".
2. Система должна уточнять у Сотрудника подтверждение выполнения заявки. Если Сотрудник подтверждает выполнение заявки, то статус заявки меняется на "Закрыта", иначе статус заявки меняется на "Отправлена на доработку".
3. Система должна позволять Сотруднику досрочно закрывать заявку, только если она **не** находится в статусе "Закрыта".
4. Система должна уточнять у Сотрудника подтверждение досрочного закрытия заявки. Если Сотрудник подтверждает досрочное закрытие заявки, то она переходит в статус "Закрыта", иначе статус заявки не меняется.

## 3. Управление заявками со стороны Специалиста

### FR-6. Просмотр входящих заявок

1. Система должна позволять Специалисту смотреть входящие заявки (статус заявки "Создана" или "Отправлена на доработку") от Сотрудников.
2. Система должна отображать следующие данные о входящей заявке: идентификационный номер заявки, категория проблемы, дата и время создания заявки.
3. Система должна сортировать входящие заявки по дате и времени (от старых к новым).
4. Система не должна отображать входящие заявки Специалисту, если у него есть заявка со статусом "В работе".
5. Если у Специалиста есть заявки со статусом "Отправлена на доработку" и нет заявок со статусом "В работе", то Система должна отображать ему только заявки со статусом "Отправлена на доработку".

### FR-7. Принятие заявки к исполнению

1. Если у Специалиста есть заявка со статусом "В работе", то Система запрещает ему брать заявки.
2. Если у Специалиста есть заявки со статусом "Отправлена на доработку", то Система позволяет ему брать в работу только их.
3. Если у Специалиста нет заявок со статусами "В работе" или "Отправлена на доработку", то Система должна позволять ему взять в работу заявку со статусом "Создана".
4. Система меняет статус заявки на "В работе" после того как Специалист берет заявку.

### FR-8. Просмотр принятой заявки

1. Система должна отображать Специалисту следующие данные по принятой им заявке (заявке со статусом "В работе"): идентификационный номер заявки, дата создания заявки, категория проблемы, описание проблемы, фамилия и имя Сотрудника, рабочий отдел и рабочее место Сотрудника.

### FR-9. Жизненный цикл заявки

1. Система должна позволять Специалисту закрывать заявку, находящуюся в статусе "В работе".
2. После закрытия заявки Специалистом Система переводит заявку в статус "Закрыта специалистом".

## 4. Коммуникация по заявке

### FR-10. Коммуникация по заявке

1. Система должна позволять Сотруднику/Специалисту отправлять текстовые сообщения в рамках заявки, находящейся в статусе "В работе".
2. Система должна сохранять сообщения, отправленные Сотрудником/Специалистом, в хронологическом порядке внутри истории переписки по заявке.
3. Система должна позволять Сотруднику просматривать чат по любой заявке, если история переписки существует.
4. Система должна позволять Специалисту просматривать чат **только** по заявке, находящейся в статусе "В работе".


## 5. Статистика и отчетность

### FR-11. Просмотр статистики по заявкам

1. Система должна позволять Аудитору просматривать следующую статистику по всем заявкам: общее число заявок, число заявок по статусам "Создана", "В работе", "Отправлена на доработку", "Закрыта".

### FR-12. Просмотр всех заявок в системе с сортировкой и фильтрацией

1. Система должна позволять Аудитору просматривать следующие данные всех заявок в Системе: номер заявки, статус заявки, категория заявки, имя и фамилия Специалиста, работающего с заявкой, дата и время создания заявки, дата и время закрытия заявки.
2. Система должна позволять Аудитору применять сортировку ко всем столбцам (по возрастанию/убыванию).
3. Система должна позволять Аудитору применять фильтры к следующим столбцам: статус заявки, категория заявки, имя и фамилия Специалиста, работающего с заявкой. Под применением фильтров подразумевается выбор отображаемых значений, например, с помощью фильтра к столбцу заявок можно отобразить заявки только со статусом "Закрыта" или заявки со статусом "Создана" и "В работе".

## 6. Настройка системы

### FR-13. Настройка категорий проблем

1. Система должна позволять Администратору просматривать, создавать, удалять категории проблем.
2. Система должна не позволять создавать категории проблем с одинаковыми названиями.

### FR-14. Настройка рабочих отделов

1. Система должна позволять Администратору просматривать, создавать, удалять названия рабочих отделов.
2. Система должна не позволять создавать рабочие отделы с одинаковыми названиями.

# Нефункциональные требования

1. Сервис должен иметь десктопную и мобильную версии сайта, поддерживаемые актуальными версиями основных браузеров: Mozilla Firefox, Google Chrome, Apple Safari, Yandex Browser. 
2. Сервис должен иметь систему авторизации по Bearer Token (JWT).
3. При создании аккаунта пароль должен хэшироваться.
4. Сервис должен поддерживать русский язык.
5. Сервис должен поддерживать работу для 4 ролей: Сотрудник, Специалист, Аудитор, Администратор.
6. Сервис должен обеспечивать целевое время отклика при 150 одновременных пользователях.
7. Время выгрузки списка всех заявок для Аудитора не должно превышать 5 секунд.
8. Время создания новой заявки не должно превышать 2 секунд.
9. Время выполнения всех остальных операций не должно превышать 0,5 секунды.
